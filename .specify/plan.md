# Implementation Plan: craftnight MVP

**Date**: 2026-05-03
**Spec**: .specify/spec.md

---

## Summary

craftnight is a SvelteKit application with a Drizzle + Postgres data layer, deployed via Docker Compose on a single DigitalOcean Droplet. The architecture is deliberately boring: server-rendered pages with progressive enhancement, form actions, signed cookies, and two third-party notification APIs (Resend, Twilio). There is no client-side state management and no token storage table. The organizer UI is built as part of the same app under a protected `/organizer/*` prefix.

## Constitution Check

✅ **SvelteKit + Drizzle + Postgres**: Stack matches exactly.
✅ **Privacy is structural**: No social graph, no contact harvesting. Guest data never appears in URLs or public HTML (NF-005). Cloudflare Web Analytics is cookie-free and non-fingerprinting.
✅ **No account required to view or RSVP**: Public pages are server-rendered. Core content present in initial HTML (NF-001 revised). Turnstile and analytics are progressive enhancements.
✅ **Self-hosted**: Docker Compose, single Droplet, organizer controls the data. Cloudflare Tunnel removes the need to open inbound ports — better security posture, no firewall management.
✅ **TypeScript**: Drizzle schema inference + SvelteKit generated route types provide end-to-end safety.
✅ **Cloudflare R2**: Images stored in existing public bucket. No filesystem uploads on Droplet. Eliminates volume backup concern.
✅ **Cloudflare Tunnel**: `cloudflared` as a Compose service. No public inbound ports on Droplet. Cloudflare handles SSL.
✅ **Cloudflare Turnstile**: Applied to subscribe/RSVP form. Server action validates token before processing. Privacy-respecting, no user puzzles.
✅ **Cloudflare Web Analytics**: Script tag injected into public event pages. Cookie-free.
⚠️ **Blast within 60 seconds for 100 subscribers**: Sequential delivery in a single server action. At ~300ms per API call, 100 subscribers ≈ 30 seconds — within NF-004. Upgrade path to parallel delivery if subscriber count grows.

## Data Model

### events

**Purpose**: The persistent named event that guests subscribe to. Root entity.

**Fields**:
- `id`: UUID, primary key, default `gen_random_uuid()`
- `name`: text, not null
- `slug`: text, not null, unique — used as `/events/[slug]` URL
- `description`: text, nullable
- `cover_image_url`: text, nullable — relative path to uploaded file (e.g., `/uploads/filename.jpg`)
- `accent_color`: text, nullable — hex string e.g. `#e85d04`
- `created_at`: timestamp with time zone, default now()

**Indexes**: `slug` (unique — used on every public page load)

**Lifecycle**: Created by organizer. Never deleted in MVP.

---

### instances

**Purpose**: A specific occurrence of an Event on a given date. What guests RSVP to.

**Fields**:
- `id`: UUID, primary key, default `gen_random_uuid()`
- `event_id`: UUID, not null, FK → events.id
- `date`: date, not null
- `start_time`: time, not null
- `end_time`: time, not null — required for ICS DTEND and schema.org/Event endDate
- `location`: text, nullable
- `blast_sent_at`: timestamp with time zone, nullable — set when announcement blast fires; prevents re-send
- `reminder_sent_at`: timestamp with time zone, nullable — set when reminder blast fires
- `created_at`: timestamp with time zone, default now()

**Indexes**: `event_id` (for listing instances per event); `(event_id, date)` (for finding upcoming instance)

**Lifecycle**: Created by organizer. Never deleted in MVP. Past instances become read-only.

---

### subscribers

**Purpose**: A guest's opt-in to receive notifications for a specific Event. Stable UUID is the identity key.

**Fields**:
- `id`: UUID, primary key, default `gen_random_uuid()` — stored in cookie and JWT
- `event_id`: UUID, not null, FK → events.id — scoped per event
- `name`: text, not null
- `email`: text, nullable
- `phone`: text, nullable — stored in E.164 format (e.g., `+14155552671`)
- `active`: boolean, not null, default true
- `created_at`: timestamp with time zone, default now()

**Constraints**:
- Check: `email IS NOT NULL OR phone IS NOT NULL` — at least one contact method required
- Unique: `(event_id, email)` where email is not null
- Unique: `(event_id, phone)` where phone is not null

**Indexes**: `event_id`; `(event_id, email)`; `(event_id, phone)` (for identity resolution lookups)

**Lifecycle**: Created on first subscribe. `active = false` on unsubscribe. Can be reactivated on re-subscribe.

---

### rsvps

**Purpose**: A single subscriber's RSVP status for a single Instance.

**Fields**:
- `id`: UUID, primary key
- `subscriber_id`: UUID, not null, FK → subscribers.id
- `instance_id`: UUID, not null, FK → instances.id
- `status`: text, not null — one of `'yes'`, `'maybe'`, `'no'`
- `created_at`: timestamp with time zone, default now()
- `updated_at`: timestamp with time zone, default now()

**Constraints**:
- Unique: `(subscriber_id, instance_id)` — one RSVP per subscriber per instance

**Indexes**: `instance_id` (for headcount queries); `(subscriber_id, instance_id)` (for upsert)

**Lifecycle**: Created or upserted when guest submits RSVP form or SMS reply. Immutable after instance date passes.

---

### blast_log

**Purpose**: Delivery record for each individual notification sent. Enables failure surfacing and auditability.

**Fields**:
- `id`: UUID, primary key
- `instance_id`: UUID, not null, FK → instances.id
- `subscriber_id`: UUID, not null, FK → subscribers.id
- `blast_type`: text, not null — `'announcement'` or `'reminder'`
- `channel`: text, not null — `'email'` or `'sms'`
- `status`: text, not null — `'sent'` or `'failed'`
- `error`: text, nullable — error message if failed
- `sent_at`: timestamp with time zone, default now()

**Indexes**: `(instance_id, blast_type)` (for organizer failure count display)

**Lifecycle**: One row appended per delivery attempt. Never updated.

## Architecture Decisions

### Decision 1: Stateless organizer session (no session table)

**Context**: NF-002 requires `httpOnly` signed cookie with 24-hour expiry and no server-side session table.

**Decision**: HMAC-SHA256 signed cookie. Payload is `{ exp: unixTimestamp }`. Signature is `HMAC(secret, JSON.stringify(payload))`. Both are base64-encoded and concatenated as the cookie value. `auth.js` exposes `createSession(res)`, `verifySession(cookieHeader)`, and `clearSession(res)`.

**Rationale**: No library dependency needed. Node's `crypto` module handles HMAC. Simple enough to audit in 20 lines. Organizer credentials (email + bcrypt hash) live in env vars — single organizer, no user table needed.

**Alternatives Considered**:
- `iron-session`: Would work but adds a dependency for a single use case.
- Lucia / Auth.js: Overkill for a single-organizer app.

**Consequences**:
- Positive: No session table, no DB hit on every request, easy to invalidate by changing the secret.
- Negative: Cannot invalidate a specific session without rotating the secret (acceptable for MVP).

---

### Decision 2: Subscriber identity as signed cookie containing event-scoped UUIDs

**Context**: Subscribers are per-event. A guest may attend multiple events. FR-008 requires a persistent cookie. FR-006 requires a stable UUID as the identity key.

**Decision**: A single `craftnight_id` cookie containing a HMAC-signed JSON object: `{ [eventSlug]: subscriberUUID, ... }`. On each public page load, the route reads the relevant slug's UUID from the cookie and looks up the Subscriber.

**Rationale**: One cookie handles multiple events gracefully. Signing the whole JSON blob prevents tampering with any UUID. Cookie path is `/` so it's sent on all routes.

**Alternatives Considered**:
- One cookie per event (path-scoped): More isolated but harder to manage and read in hooks.
- Store contact info in cookie: Never — violates NF-005 and the privacy constitution value.

**Consequences**:
- Positive: Works across multiple events; single cookie to manage.
- Negative: Cookie grows slightly with each new event subscription — negligible at this scale.

---

### Decision 3: Subscriber tokens as stateless JWTs (no token table)

**Context**: FR-018 requires signed tokens in notification links. FR-019 requires token-based identification on arrival. NF-006 requires 30-day expiry.

**Decision**: HS256 JWTs via `jose`. Payload: `{ sub: subscriberUUID, eventId, exp: now + 30 days }`. Signed with `JWT_SECRET` env var. On arrival, verify signature and expiry, look up subscriber, set/refresh cookie.

**Rationale**: Stateless — no DB table, no cleanup job. `jose` is a modern, well-maintained JOSE implementation that works in Node and edge runtimes. Token expiry is enforced by the library.

**Alternatives Considered**:
- `jsonwebtoken`: Older library, some ESM roughness. `jose` is cleaner.
- DB token table: Adds write path on every blast, plus cleanup. Overkill.

**Consequences**:
- Positive: No storage, no cleanup, scales to any blast size.
- Negative: Cannot invalidate a specific token before expiry (acceptable — token just sets a cookie, doesn't grant write access by itself; RSVP locks are enforced by instance date).

---

### Decision 4: Cover image storage in Cloudflare R2

**Context**: Events have cover images (FR-003, FR-023, FR-030). The app is self-hosted on a single Droplet but the organizer already has an existing public R2 bucket.

**Decision**: Organizer uploads image via multipart form. The server action streams the file to R2 using `@aws-sdk/client-s3` (R2 is S3-compatible) via `src/lib/server/r2.ts`. The stored `cover_image_url` is the full public R2 URL. No files are written to the Droplet filesystem.

**Rationale**: Images live outside the Droplet entirely — no Docker volume to back up, no data lost on Droplet migration or rebuild. Egress is free via Cloudflare's CDN. The organizer is already paying for R2 and has a public bucket configured, so there is no additional cost or setup required.

**Alternatives Considered**:
- Filesystem + Docker volume: Simpler code but creates a stateful dependency on the Droplet. Images are lost if the volume is not explicitly preserved during redeployment.
- Accept URL only (no upload): Requires the organizer to host images elsewhere before creating an event — unnecessary friction.
- DigitalOcean Spaces: Would work but adds a second object storage account and credentials when R2 is already available.

**Consequences**:
- Positive: Stateless Droplet — can be rebuilt or replaced without data loss. Images served via Cloudflare CDN with no egress fees.
- Negative: Requires R2 credentials in env vars (`R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`, `R2_PUBLIC_URL`). Upload adds one external API call to the event create action.

---

### Decision 5: Blast delivery as synchronous server action

**Context**: NF-004 requires blasts complete within 60 seconds for ≤100 subscribers.

**Decision**: The blast server action iterates subscribers sequentially, calling Resend or Twilio for each. Each result is written to `blast_log`. The action does not return until all deliveries are attempted. `instances.blast_sent_at` is set before iteration begins to prevent re-entry.

**Rationale**: At ~200-400ms per API call, 100 subscribers = 20-40 seconds — within the 60-second window. Sequential is easy to reason about and debug. Failure logging per-subscriber surfaces partial failures to the organizer.

**Alternatives Considered**:
- `Promise.allSettled` (parallel): Faster but risks rate limiting from Resend/Twilio on burst.
- Background job / queue: Right for production scale, wrong for MVP complexity budget.

**Consequences**:
- Positive: Simple, debuggable, no worker infrastructure.
- Negative: Server action holds open for up to ~40 seconds. SvelteKit handles this fine on Node. Upgrade path is clear if subscriber count grows.

---

### Decision 6: Identity resolution order (FR-006b)

**Context**: A guest may re-submit the subscribe form with an email or phone that already exists in the subscriber list.

**Decision**: `subscribers.js` implements the priority lookup in order:
1. Cookie UUID match — look up by `subscribers.id` scoped to the current `event_id`
2. Email match — `SELECT * FROM subscribers WHERE event_id = ? AND email = ? AND active = true`
3. Phone match — same pattern
4. Create new Subscriber record

On match via step 2 or 3, record the RSVP but do not update the subscriber's name (per clarification: keep original name on re-subscribe). Set/refresh the cookie with the matched UUID.

**Rationale**: This handles all the edge cases in the spec (duplicate email, duplicate phone, returning cookie guest) in one deterministic function. Centralizing in `subscribers.js` keeps the route action thin.

**Consequences**:
- Positive: Correct behavior for all known edge cases; easy to test.
- Negative: Three potential DB reads before creating a record — acceptable at this scale.

### Block 6: P2 Features
**Dependencies**: Block 5
**Builds**: Reminder blast (US8 — yes/maybe only), Twilio inbound webhook + signature validation (US11), SMS reply RSVP parsing + confirmation
**Why this block**: P2 — adds value but not required for first real use
**Verification checkpoint**: Reminder blast reaches only yes/maybe subscribers; SMS reply "yes" updates RSVP and replies with confirmation; invalid Twilio signature returns 403

## Complexity Notes

- **Subscriber identity resolution** (Phase 5) is the most nuanced logic in the codebase. The 4-step priority lookup must be correct — incorrect matching would create duplicate subscribers or merge unrelated guests. Test this function in isolation before wiring it to the route.
- **Twilio inbound webhook** (Phase 7) requires careful phone number normalization. Twilio delivers numbers in E.164; stored subscriber phones must also be E.164 for the match to work. Normalize on write (Phase 5) and validate on inbound.
- **Blast timing** (Phase 6): Set `blast_sent_at` *before* iterating subscribers. If the action throws mid-blast, re-triggering is blocked — preferable to sending duplicates.
- **RSVP locking** (Phase 5): The `isPast` check must compare instance `date` against server time (not client time) to enforce NF lockout correctly. Date-only comparison is sufficient — lock at midnight on the event date.
